# Harness Evidence

This directory is the durable record of the reviewed baseline, every harness run, and the
human acceptance decision. The runner writes per-run artifacts append-only; do not edit or
delete prior results, logs, manifests, or snapshots.

## Layout

```text
evidence/
├── baseline/
│   ├── protected-inputs.sha256
│   ├── harness-control.sha256
│   ├── acceptance-test-inventory.json
│   └── amendments/
│       └── <version>/
│           ├── protected-inputs.sha256
│           ├── harness-control.sha256
│           ├── approved-artifacts.sha256
│           ├── amendment.md
│           └── revisions/
│               └── <revision>/
│                   ├── protected-inputs.sha256
│                   ├── harness-control.sha256
│                   ├── approved-artifacts.sha256
│                   └── amendment.md
├── initial/
│   ├── implementation/
│   ├── implementation.sha256
│   └── runs/<run-id>/
│       ├── results.json
│       ├── run.log
│       ├── run.sha256
│       ├── logs/<check-id>.stdout.log
│       ├── logs/<check-id>.stderr.log
│       └── agent-feedback.json   # only when checks genuinely fail
├── repairs/
│   └── round-<n>/
│       ├── implementation/
│       ├── implementation.sha256
│       └── runs/<run-id>/        # same run artifacts as initial/
├── final/
│   ├── implementation/
│   ├── implementation.sha256
│   ├── revisions/<n>/            # immutable later final snapshots
│   └── runs/<run-id>/            # same run artifacts as initial/
└── human-decision.json            # written by a human, never generated by the runner
```

T019 freezes specification, contract, harness-control, package-script, and lockfile hashes,
plus the acceptance-test inventory, only after all acceptance tests are created and
human-reviewed and before application implementation. Integrity verification does not create
baselines. Missing baselines cannot produce `PASS` (`BLOCKED` when there are no other
integrity findings); any change requires human review and an explicit, retained re-baseline.
Keep the original T019 files and prior amendment revisions unchanged. Store approved
amendments in numbered directories and follow-up revisions in `revisions/<revision>/`; point
`policy.json` at the active protected-input and harness-control manifests. Each revision records
old and new hashes and its rationale; the checker reads the active paths from the policy.

Snapshots contain source and test files plus selected root configuration/package files.
The runner excludes dependencies, generated build output, runtime task data, specs, harness
controls, and existing evidence. Each snapshot manifest records SHA-256 hashes. Snapshots are
write-once: a changed implementation cannot replace an existing phase snapshot. The runner
refuses to rerun that phase against a changed tree; record repairs in a new round and capture
the final snapshot only after selecting the final candidate.

## Initial, repair, and final runs

After the reviewed baseline and acceptance tests exist and the first implementation is ready,
capture and validate the initial state:

```powershell
node .harness/run.mjs --phase initial
```

For each repair, preserve the current candidate and rerun the unchanged full matrix:

```powershell
node .harness/run.mjs --phase repair --round 001
```

Use a new round number for each subsequent repair. At the end, snapshot and run the complete
matrix, even if failures remain:

```powershell
node .harness/run.mjs --phase final
```

If `evidence/final/` already contains an immutable snapshot, preserve it and create a
versioned final snapshot and full-matrix run:

```powershell
node .harness/run.mjs --phase final --revision 002
```

The snapshot and manifest are written under `evidence/final/revisions/002/`; the run remains
under `evidence/final/runs/<run-id>/` and records the exact snapshot-manifest path.

Every completed run has a unique directory. Its result and logs are retained with a
`run.sha256` manifest; genuine `FAIL` outcomes also have schema-validated AI feedback. The
feedback references actual check results and logs. `BLOCKED` outcomes are not described as
failures or passes.

## Human review

After reviewing the final run, a human authors `human-decision.json` according to
`schemas/human-decision.schema.json`. Include `ACCEPT` or `REJECT`, reviewer, UTC timestamp,
final run ID, rationale, and known limitations. The runner never invents reviewer details or
automatically accepts a passing run.

Validate the authored record with:

```powershell
node .harness/run.mjs --validate-decision
```

The record must reference the latest final run. `ACCEPT` is valid only when every check in
that run passes; otherwise document a `REJECT` and rationale. A later final run makes a
decision referencing an older run stale and requires renewed human review.
