# Tasks: Smart Todo Management API

**Input**: Design documents from `specs/001-smart-todo-api/`

**Prerequisites**: `plan.md`, `spec.md`, `data-model.md`, `contracts/openapi.yaml`,
`research.md`, `quickstart.md`, and `.specify/memory/constitution.md`

**Tests**: Unit, integration, and HTTP contract tests are required by the specification and
constitution. Write story tests before their implementation tasks and verify the initial failures.

**Organization**: Tasks are grouped by the three user stories in `spec.md`. The application
tests assert API behavior; `.harness/` independently runs and records those tests along with
syntax, lint, type, security, coverage, and integrity checks.

## Path Conventions

Application paths are relative to the `Part-1A/` project root. Evidence snapshots and run
records are generated by the harness; do not create passing results manually.

## Dependencies & Execution Order

### Phase Dependencies

- **Setup (Phase 1)**: T001 first; T002 and T003 can run in parallel after T001.
- **Foundational (Phase 2)**: Depends on Setup. The fixed policy precedes schemas/checks; integrity checks and syntax parsing can proceed in parallel; the runner depends on those components.
- **Acceptance-Test Authoring (Phase 3)**: Depends on Foundation. All acceptance tests for US1, US2, and US3 are written and reviewed before application implementation; test-file extensions follow their prerequisite tasks to avoid concurrent edits.
- **Pre-implementation Baseline (T019)**: Depends on all Phase 3 test tasks. Freeze the protected inputs, scripts/lockfile, and complete acceptance-test inventory before any application implementation task.
- **User Story 1 (Phase 4)**: Depends on the pre-implementation baseline; implementation follows model → store → service → routes → server.
- **User Story 2 (Phase 5)**: Depends on User Story 1 because it hardens the existing API, validation, and store; implementation tasks are ordered because they extend shared files and behavior.
- **User Story 3 (Phase 6)**: Depends on User Story 2's validation and route foundation; implementation proceeds query validation → service filtering/sorting → route integration.
- **Polish (Phase 7)**: Depends on all user stories. Initial capture precedes any harness-driven repair; final evidence and human decision follow the last full validation.

### User Story Dependencies

- **US1 (P1)**: Depends on Setup, Foundation, and the reviewed pre-implementation baseline; delivers the CRUD MVP.
- **US2 (P1)**: Depends on US1's API and persistence implementation; adds the specified validation and durability guarantees.
- **US3 (P2)**: Depends on US2's query-validation and route foundation; adds list filtering and deterministic sorting.

### Parallel Opportunities

- Setup: T002 and T003 after T001.
- Foundation: T006 and T007 after the policy/schema definitions are agreed.
- Initial tests in separate files T011-T014 can be authored in parallel. Then T015-T017 can proceed in parallel after their referenced files exist; T018 follows T016. Record baseline T019 only after every acceptance-test task is complete.
- User stories are intentionally sequenced because later stories extend shared service, validation, persistence, route, and test files.

## Implementation Strategy

### MVP First

Complete Setup and Foundation, author all story tests, and record baseline T019; then implement
US1 for a demonstrable CRUD slice. US1 alone is not assignment-complete: US2's P1 validation,
persistence, and reliability guarantees are also required before acceptance.

### Incremental Delivery

1. Complete Setup and Foundation; author all story acceptance tests.
2. Record and review the protected-input, package, and acceptance-test inventory baseline.
3. Implement and independently test US1 CRUD.
4. Implement and independently test US2 validation and durability.
5. Implement and independently test US3 filtering and sorting.
6. Capture initial evidence, repair only from genuine failures with a full matrix each round, and
   produce final evidence plus a human decision.

## Notes

- Every task uses the required checkbox, sequential ID, optional `[P]`, story label for story
  tasks, and concrete file path.
- `[P]` is reserved for tasks on separate files with no dependency on unfinished work.
- The approved `spec.md`, OpenAPI contract, constitution, harness policy, and acceptance tests are
  not to be weakened to obtain passing results.
- Task field constraints are referenced to `data-model.md` by exact `Task.field` in implementation
  tasks; that document remains the canonical source.
